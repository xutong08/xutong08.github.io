从零搭建 Hexo 博客（详解版）：每个工具、每条命令到底在做什么

网上大部分 Hexo 教程的问题是：只告诉你「输入这条命令」，却不说为什么是这条命令、输完之后电脑干了什么、出了错该怀疑谁。

这篇文章整理自 BaiYB 的 Hexo 搭建教程，我用自己的话重新梳理了一遍，重点补上三件事：

  • 每个工具到底是干什么的；
  • 每项设置背后的原理；
  • 每条命令逐词解释。

我自己用的是 macOS，原教程以 Windows 为主，所以两边的差异我都会标注。

二、六个工具分别是干什么的

工具 角色 一句话理解
Node.js 运行环境 Hexo 是用 JavaScript 写的，需要 Node.js 才能跑起来
npm 包管理器 跟着 Node.js 一起安装，负责下载 Hexo、插件、主题依赖
Git 版本管理工具 下载主题、把博客上传到 GitHub 都靠它
GitHub 代码托管平台 存放仓库，并通过 GitHub Pages 把网站发布到互联网
Hexo 静态博客框架 把 Markdown 文章转换成静态网页
Butterfly 主题 决定博客最终长什么样

「静态」的意思是：网页在你自己电脑上就已经生成好了，服务器不需要运行数据库、不需要实时计算，只负责把文件发给访客，所以免费托管、访问速度快。

3.3 GitHub 账号

注册地址：https://github.com/signup。注册后记住自己的用户名和邮箱，后面配置 Git 和 SSH 时都要用。

3.4 网络前提

初始化 Hexo、克隆主题、部署都会访问 GitHub。请先确认浏览器能正常打开 https://github.com。如果网页都打不开，后面出现 Connection timed out、Connection reset 这类报错就很正常了——先解决网络，别怀疑 Hexo。

五、部署到 GitHub Pages

GitHub Pages 是 GitHub 提供的免费静态网页托管服务，和仓库无缝配合，特别适合 Hexo。

Step 1：创建规定名称的仓库

在 GitHub 点 New repository，仓库名必须严格写成：

比如用户名是 xutong08，仓库就叫 xutong08.github.io。

为什么必须这么命名？ 这是 GitHub Pages「用户站点」的规则：只有叫 用户名.github.io 的仓库，GitHub 才会把它发布到 https://用户名.github.io 这个根域名。随便起名的话网址会变成 用户名.github.io/仓库名 的子路径。

Step 2：告诉 Git「你是谁」

  • git config：修改 Git 的配置；
  • --global：对当前电脑上所有仓库生效（不加就只对当前仓库生效）；
  • user.name / user.email：提交记录里的作者身份，GitHub 靠邮箱把提交和你的账号对应起来。

Step 3：理解并生成 SSH Key（重点）

为什么需要它？ 部署时要把代码推送到 GitHub，如果用密码，每次都要手动输入而且 GitHub 早已不支持密码推送。SSH Key 的方案是生成一对钥匙：

  • 私钥 id_rsa：留在自己电脑上，绝不能发给任何人；
  • 公钥 id_rsa.pub：放到 GitHub 上，可以公开。

推送时 GitHub 用公钥验证你持有对应的私钥，整个过程不需要密码，也无法伪造。

生成命令：

  • ssh-keygen：SSH 密钥生成工具；
  • -t rsa：-t 指定密钥类型为 RSA（一种非对称加密算法）；
  • -C 邮箱：-C 是 comment（备注），在密钥末尾附上邮箱方便辨认，不影响功能。

之后会询问保存位置和密码，第一次用直接一路回车，采用默认设置、不设密码即可。

默认位置：

  • Windows：C:\Users\你的用户名\.ssh\id_rsa.pub
  • Mac：~/.ssh/id_rsa.pub（~ 代表用户主目录，即 /Users/你的用户名）

用记事本或文本编辑器打开 id_rsa.pub，复制里面的全部内容。注意是带 .pub 的公钥，不是私钥。

Step 4：把公钥添加到 GitHub

打开 https://github.com/settings/ssh/new，把公钥粘贴到 Key 框里，Title 随便起一个方便识别的名字，比如 My Mac。

逐条解释：

  1. ssh-agent 是一个在后台帮你保管私钥的程序，eval "$(ssh-agent -s)" 是启动它并让当前终端记住它；

每配完一层就先测试这一层。 SSH 没通过就不要去部署，否则最后只会看到一大串报错，却不知道问题早就出在前面。

九、常见报错与排查

1. hexo 不是内部或外部命令
先确认 node -v、npm -v 正常，再重装 npm install -g hexo-cli，重开终端；仍不行就检查 npm 全局路径是否在环境变量里。

2. hexo init 卡住 / 克隆失败
看到 Failed to connect、Timed out、Connection reset，先打开浏览器确认 GitHub 能访问、git --version 正常。别怀疑 Hexo，是 Git 到 GitHub 的网络不通。

3. npm install 报错
真正的原因往往在报错信息上方，从第一个 npm ERR! 开始完整复制，不要只截最后一行。依赖乱掉时备份后重新 npm install，别乱用年份不明的「万能命令」。

4. ssh -T git@github.com 失败
依次检查：密钥文件是否存在、GitHub 上添加的是不是 .pub 公钥内容、ssh-agent 是否启动、私钥是否 ssh-add 过、网络能否连 GitHub 的 SSH。

5. 部署成功但页面还是旧的
先 hexo clean 再 hexo g && hexo d；浏览器用 Ctrl + F5（Mac: Cmd + Shift + R）强制刷新；再去仓库看提交时间有没有更新，区分「没部署上 / Pages 没更新 / 浏览器缓存」三种情况。

6. 改了主题配置没反应
先确认改的是哪个 _config.yml——博客里可能有多个配置文件，很容易改错。然后 hexo clean && hexo g 清掉旧缓存。

7. 图片本地正常、部署后裂开
C:\Users\xxx\1.png 这种你电脑上的路径，对互联网上的浏览器没有任何意义。图片必须让浏览器能通过网址访问：放进 source/ 目录、用图床、文章资源文件夹或对象存储都可以。

十、怎么向 AI 提问才有效

不要只问「Hexo 报错了怎么办」，这等于没给信息。推荐这样描述：

完整报错 + 当前目录 + 执行的命令 + 已经做过什么，回答质量完全不同。AI 最有用的地方不是替你复制命令，而是帮你理清：现在知道什么、缺什么信息、下一步最该验证什么。
